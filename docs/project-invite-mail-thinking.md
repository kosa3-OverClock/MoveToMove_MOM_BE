# 프로젝트 초대 메일 로직 구현 사고 과정 (이미지 기반)

> 문서 목적: "처음엔 한 트랜잭션으로 처리했다가, 왜 비동기 분리로 사고를 바꾸게 되었는지"를 구현자 관점에서 남긴 기록

이 문서는 "프로젝트 초대 메일 시퀀스" 이미지를 기준으로, 개발자가 실제 구현할 때 어떤 생각으로 단계를 나눴는지 정리한 회고 문서입니다.

## 0) 처음 실수: 한 트랜잭션에서 DB + 메일 전송을 같이 처리

처음에는 아래처럼 단순하게 접근하기 쉽습니다.

1. `insertProjectJoins(...)`로 참여자 DB 저장
2. 같은 서비스 메서드에서 메일 발송까지 즉시 실행
3. 전부 하나의 요청 흐름에서 끝내기

현재 코드에서도 초대 저장 로직과 메일 호출은 같은 서비스 메서드 안에서 이어져 있습니다.

- `ProjectService.insertProjectJoin(...)`에서 배치 insert 후 `emailService.projectInvite(...)` 호출
- `insertProjectJoin(...)`는 `@Transactional`로 묶여 있음

이 방식은 구현은 빠르지만, 메일 서버 지연/실패가 API 응답시간과 안정성에 직접 영향을 줄 수 있다는 단점이 있습니다.

## 1) 왜 구조를 다시 생각했는가

이미지의 핵심은 "요청 처리"와 "메일 전송"을 분리하는 것입니다.

- API 사용자는 "초대 요청이 접수됐는지"를 빠르게 알고 싶음
- 메일 발송은 외부 I/O(네트워크)라 느리거나 실패 가능성이 큼
- 여러 명을 초대하면 지연이 누적될 수 있음

즉, **DB 반영(핵심 트랜잭션)**과 **알림 발송(부가 작업)**을 분리해야 운영이 편해집니다.

## 2) 이미지 기준 구현 사고 흐름

### Step A. 요청/검증 구간은 동기 처리

- 컨트롤러에서 서비스 호출
- 프로젝트 존재 여부, 권한 등 필수 검증
- 참여자 관계 데이터 저장

이 단계는 "정합성"이 중요하므로 동기로 확실히 끝냅니다.

### Step B. 메일 발송은 비동기로 전환

현재 코드의 `EmailService.projectInvite(...)`는 `@Async`로 선언되어 있어,
서비스가 메일 작업을 위임하고 요청 스레드를 빨리 반환할 수 있습니다.

- `EmailService.projectInvite(...)`에 `@Async`
- 애플리케이션에 `@EnableAsync` 활성화

즉, 처음의 "한 덩어리 처리"에서 "핵심 트랜잭션 + 비동기 후처리"로 사고를 바꾼 것입니다.

### Step C. 멤버 단위 처리로 쪼개기

초대는 본질적으로 N명의 수신자에게 독립적으로 처리됩니다.

- 현재 구현도 `memberDtoList.forEach(...)`로 멤버별 발송을 수행
- 한 명 성공/실패가 다른 수신자와 분리됨

이미지에서 표현된 "멤버별 상태 관리"(PENDING/SUCCESS/FAILED)는,
현재 코드에는 아직 명시적으로 없지만 다음 개선 단계로 매우 자연스럽습니다.

## 3) 이미지와 현재 코드의 대응표

- "프로젝트 참여자 저장" → `projectJoinMapper.insertProjectJoins(...)`
- "메일 서비스 호출" → `emailService.projectInvite(...)`
- "비동기 워커" → `@Async` 메서드 실행
- "실제 전송" → `JavaMailSender` + `sendEmail(...)`

## 4) 구현하면서 체크해야 하는 현실 포인트

1. **API 응답 기준 정의**
   - "메일 성공"이 아니라 "초대 요청 접수"를 성공 기준으로 둘지 결정
2. **실패 관측성**
   - 현재는 로그 기반 성공/실패 기록
   - 운영 안정성을 위해선 멤버 단위 상태 테이블/재시도 정책 추가 고려
3. **트랜잭션 경계**
   - DB 정합성(초대 관계 저장)과 외부 I/O(메일 전송) 경계를 분리
4. **대량 초대 성능**
   - 수신자 수 증가 시 비동기 큐/재시도 백오프/서킷브레이커 도입 검토

## 5) 한 줄 정리

처음에는 "초대 저장 + 메일 전송"을 한 번에 처리했지만,
운영 관점에서 **핵심 트랜잭션은 짧게, 메일은 비동기 후처리로 분리**하는 쪽이 더 안전하고 확장에 유리하다는 판단으로 로직을 발전시키는 흐름입니다.

## 6) 그래서, 현재 구현은 메일 기능에 "맞는" 구현인가?

결론: **기본 기능은 맞고 동작 가능하지만, 운영 안정성까지 고려하면 개선 여지가 큽니다.**

### 지금 방식의 장점

- `@Async`로 요청 지연을 줄이려는 방향은 적절함
- 멤버 목록 반복 처리로 다수 수신자 발송이 가능함
- 이미 서비스 분리(`ProjectService` ↔ `EmailService`)가 되어 있어 개선 진입이 쉬움

### 지금 방식의 한계

- 비동기 실패가 DB 상태와 분리되어 "누가 실패했는지" 추적이 어려움
- `@Async` 메서드에서 예외가 나면 재시도/복구 정책이 명확하지 않음
- 트랜잭션 안에서 비동기 호출 시점이 커밋 타이밍과 엇갈릴 여지가 있음

## 7) 조금 더 괜찮은 방법 (추천 순서)

### 1단계: 최소 변경으로 안정성 올리기

1. 멤버별 발송 성공/실패 로그를 구조화(프로젝트ID, 이메일, 에러코드)
2. `@Async` 전용 `TaskExecutor`를 분리해 스레드 풀 크기/큐 제한 설정
3. 메일 발송 실패 시 재시도(예: Spring Retry)와 최종 실패 로그 분리

### 2단계: 운영형 구조로 확장

1. 초대 상태 테이블 도입 (`PENDING`, `SUCCESS`, `FAILED`)
2. API 트랜잭션에서는 상태를 `PENDING`으로 저장만 수행
3. 커밋 이후 이벤트를 비동기로 소비해 메일 전송
4. 성공 시 `SUCCESS`, 실패 시 `FAILED` + 실패 사유 업데이트

이렇게 하면 이미지에서 말한 "부분 성공 허용 + 재처리 가능" 구조를 실제 운영 수준으로 구현할 수 있습니다.

### 3단계: 대규모 트래픽 대응

- Outbox 패턴 + 메시지 브로커(Kafka/RabbitMQ)로 분리
- 메일 발송 워커를 독립 배포해 수평 확장
- 일시 장애 시 재처리(backoff, DLQ) 가능하게 설계

## 8) 실무적으로 권장하는 기준선

작은 팀/초기 서비스라면
"현재 구조 + (재시도/상태추적/Executor 분리)" 만 해도 체감 안정성이 크게 올라갑니다.

트래픽이 커지거나 발송 중요도가 높아지면
"상태 테이블 + 커밋 후 비동기 이벤트 + Outbox" 조합으로 가는 것을 권장합니다.

## 9) 빠른 체크리스트 (적용 우선순위)

- [ ] `@Async` 전용 `TaskExecutor` 설정 (core/max/queue)
- [ ] 메일 실패 재시도 정책(Spring Retry)과 최종 실패 로그 분리
- [ ] 초대 건 상태 컬럼(`PENDING/SUCCESS/FAILED`) 및 실패 사유 저장
- [ ] 커밋 후 발행 방식(`@TransactionalEventListener`) 검토
